## 修复点击打包导致界面假死（commit `514bb96`）

用户反馈「点击打包造成应用界面假死」。

### 根因（典型坑，务必记住）
`start_pack` 里后台线程写成：
```rust
let mut buf = log.lock().unwrap();     // ← 打包开始就拿住锁
let res = pack_core(..., &mut buf);    // 压缩大包耗时数十秒~数分钟
drop(buf);                             // ← 直到结束才释放
```
整段打包期间 Mutex guard 一直被后台线程持有，UI 线程任何
`self.log.lock()`（渲染日志页、保存配置、清空日志）都会阻塞，
Windows 随即把窗口判定为「无响应」。

### 修复原则：跨线程共享状态绝不在长任务期间持锁
- `pack_core` 的日志参数由 `&mut Vec<String>` 改为 `impl FnMut(&str)` 回调；
  调用方改成「每写一条 → 短暂加锁 → 立即释放 → `ctx.request_repaint()`」
- 新增 `push_log(&Arc<Mutex<Vec<String>>>, &str)`：`try_lock` + 忽略失败，
  锁被 poison 也不 panic
- UI 线程侧日志读取全部 `try_lock`，取不到就跳过本帧
  （日志页显示「（日志正被写入，稍后刷新）」），**绝不阻塞 UI 线程**
- `running` 状态读取同样 `try_lock`（只有起止瞬间短暂写锁，可阻塞式写）

### 附带体验改进
- 打包期间 `ui.ctx().request_repaint()` 持续重绘 → 日志实时刷新、spinner 转动
- 顶部「打包」按钮旁加 `ui.spinner()` +「打包中…」
- 点击打包后自动切到日志页
- 失败日志去掉 emoji（中文字体缺字形易变豆腐块），改「[失败] 打包失败: …」

### 防回归测试（新增）
`log_lock_not_held_during_pack`：后台线程跑 `pack_core`（4MB 不可压缩数据），
主线程在 `while !handle.is_finished()` 里忙等并反复 `try_lock`，
断言至少取到一次锁——取不到即说明锁被长期占用（假死回归）。
4 个用例全过。
